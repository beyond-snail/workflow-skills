# 项目驾驶舱页面线框图

## 设计目标

这不是任务管理后台，而是一个“首页选项目 + 项目页看任务”的双层驾驶舱。

目标只有三个：

1. 一眼看懂有哪些项目
2. 一眼看懂每个项目处于什么阶段
3. 点进项目后，一眼看懂当前在做什么、卡在哪里、证据是否齐

---

## 布局契约

- 首页固定一屏，采用九宫格项目墙
- 项目页固定一屏，采用三栏驾驶舱
- 首页只负责选项目，不承载任务细节
- 项目页只负责当前项目的执行情况
- 溢出内容只允许在区域内滚动
- 生命周期只用紧凑状态条，不再单独占大块
- 右侧详情只显示一个标签页，不同时堆多个模块

---

### 首页卡片职责

首页卡片只回答 4 个问题：

- 这是什么项目
- 现在处在哪个阶段
- 风险高不高
- 值不值得点进去

### 首页卡片内容

每张项目卡建议只放这些字段：

- 项目简称
- 项目全名
- 当前阶段
- 风险等级
- 当前任务数
- 最近更新时间

### 首页交互

- 点击项目卡进入项目页
- 点击 `+ 新建项目` 打开创建面板
- 项目数超过 8 个时，首页切换分页，不允许无限向下堆

- 右下角固定一个 `+ 新建项目` 卡

4. 当前任务数
5. 最近更新时间

### 中栏

## 新建项目入口

页面里保留多个入口，但它们都指向同一个创建面板：

- 顶部右侧 `+ 新建项目`
- 左侧项目列表里的 `新增项目`
- 左侧的 `添加新项目` 卡片
- 左侧底部的 `再建一个项目`
- 中栏里的 `添加项目`

创建时的原则：
- 必填只保留 `项目名称`
- 其他字段都可选
- 不要求用户手写长描述
- 摘要自动生成

## 实时同步机制

驾驶舱的数据来源不是页面自己猜出来的，而是项目主动输出的状态快照。

### 同步目标

- 首页项目卡显示的是最新项目状态
- 项目页显示的是当前任务、证据和风险的最新值
- 页面上能明确看出数据是何时同步的

### 同步方式

建议同时支持三种方式：

1. 文件监听
   - 监听本地项目目录里的状态文件变化
   - 适合本地路径项目，比如 `erp-finance`
   - 一旦状态文件更新，驾驶舱立即刷新

2. 定时轮询
   - 每隔一段时间自动检查一次项目状态
   - 适合作为文件监听的兜底
   - 建议间隔 10 到 30 秒

3. 手动刷新
   - 页面提供一个刷新按钮
   - 用户可以随时强制拉取最新状态
   - 适合作为最终兜底

### 单一事实源

不要让驾驶舱自己拼很多分散文件去猜状态。  
建议每个项目都输出一个统一的状态快照文件，例如：

- `project-state.json`
- 或 `.ai/runtime/project-status.json`

这个快照最好在 `workflow-bootstrap` 初始化底座时就创建出来，后续由 `workflow-requirement` 和 `workflow-execution` 持续回写增量内容。

也就是说：

- `workflow-bootstrap` 负责生成快照骨架
- `workflow-requirement` 负责补需求和任务字段
- `workflow-execution` 负责补任务进度、证据和验证字段
- 驾驶舱只读取这个快照，不直接拼散文件

这个文件由 workflow 的各个阶段持续回写，驾驶舱只读取它。

### `project-state.json` 骨架示例

`workflow-bootstrap` 初始化底座时，可以先生成一个最小骨架：

```json
{
  "id": "erp-finance",
  "name": "ERP 财务管理系统",
  "path": "/Users/wucongpeng/Documents/jty-work/erp-finance",
  "stage": "requirement",
  "gateStatus": "待人工审核",
  "owner": "财务协作组",
  "lastSyncAt": "2026-04-10 09:38",
  "health": "观察中",
  "risk": "中",
  "metrics": {
    "totalTasks": 0,
    "doing": 0,
    "blocked": 0,
    "review": 0,
    "done": 0,
    "evidenceCoverage": 0
  },
  "sync": {
    "source": "bootstrap",
    "status": "fresh"
  }
}
```

后续 `workflow-requirement` 和 `workflow-execution` 只做增量补充：

- 补任务
- 补证据
- 补风险
- 补时间线
- 更新 `lastSyncAt`

### 页面必须显示的同步信息

- 最近同步时间
- 数据来源
- 同步状态

例如：

- `刚刚同步`
- `12 秒前`
- `本地扫描`
- `任务看板`
- `证据回写`
- `已同步`
- `同步中`
- `已过期`

## 卡片尺寸原则

- 同类卡片尽量等高
- 大标题只出现一次
- 字号统一收一档
- 同屏内不要出现两个“主视觉大块”
- 生命周期不要再单独占一整行大面板

---

## 本地项目接入方式

本地项目进入驾驶舱时，不是按 skill 拆卡，而是按项目路径建卡。

例如：

- `/Users/wucongpeng/Documents/jty-work/erp-finance`

驾驶舱应该把它视作一个项目实例，并从路径里扫描 workflow 资产：

- `bootstrap`：是否存在底座文件
- `requirement`：是否存在需求池、任务看板、交接材料
- `execution`：是否存在任务执行、验证、证据回写

项目卡上可以直接展示：

- 项目名
- 本地路径
- 当前阶段
- 风险等级
- 当前任务数
- 最近同步时间

## 冻结规则

后续代码实现时，优先遵守这份线框，不要因为临时想补内容就打破结构。

如果要增加新信息，优先：

1. 放进现有区域
2. 替换掉次要信息
3. 用标签页收纳
4. 最后才考虑新增区域

## 架构设计

这个驾驶舱不是独立猜状态的前端，而是一个“项目事实的展示终端”。

推荐架构分成四层：

```text
本地仓库 / 项目目录
  └── workflow 三个 skill
        ├── workflow-bootstrap
        ├── workflow-requirement
        └── workflow-execution
              └── 统一状态快照 project-state.json
                    └── 驾驶舱 React App
```

### 分工说明

#### 1. workflow-bootstrap

负责把项目底座建立起来，输出可以被驾驶舱识别的基础事实：

- AGENTS / PROJECT_CONTEXT 是否存在
- `.ai/` 是否初始化
- 工作流运行态是否可用

#### 2. workflow-requirement

负责把 PRD 或业务目标变成可执行需求：

- 需求入池
- 任务拆解
- 人工审核门
- 需求变更记录

#### 3. workflow-execution

负责把需求变成可追踪的执行过程：

- 任务推进
- 验证记录
- 证据回写
- release gate 收口

### 数据采集链路

建议所有阶段最终都回写到同一个快照文件：

- `.ai/runtime/project-state.json`
- 或 `project-state.json`

驾驶舱只读这个文件，不直接拼散文件。

### 推荐流程

```text
项目变化
  -> skill 回写事实
  -> 生成状态快照
  -> 驾驶舱轮询或监听
  -> 页面刷新展示
```

### 采集策略

- 文件监听：适合本地路径项目，更新最快
- 定时轮询：适合作为兜底
- 手动刷新：适合用户临时强制同步

### 驾驶舱展示原则

- 首页看项目，不看任务
- 项目页看任务，不看流程说明
- 右侧详情只看一个标签页
- 所有状态都要显示最近同步时间

### 你这套方案的本质

这不是“3 个 skill 的展示页”，而是：

- 3 个 skill 负责生产事实
- 驾驶舱负责消费事实
- 项目快照负责连接两者

只要这个关系不变，后面无论接多少个本地项目，都可以继续复用同一套驾驶舱模板。
