# 共享治理规则

本文件是 `workflow-requirement` 与 `workflow-execution` 的共享治理基线。
修改时必须同步另一份同名文件，保持两边文本一致。

## 核心原则

1. 业务语义永远以 `PRD` 为准，不得用历史代码口径覆盖 `PRD`。
2. 文档优先级固定为：
   `PRD` > `产品确认清单` > `PRD追溯/设计文档` > `流程图与实现对齐说明` > `联调/测试记录` > `现有代码`。
3. 不允许因为某份实现对齐文档、测试记录或现有代码已经写成某种口径，就反推 `PRD` 已满足；必须先回看 `PRD` 原文。
4. 所有“已对齐 / 未对齐 / 部分对齐”结论，必须能追溯到具体 `PRD` 条款或文件位置。
5. 发现设计文档、任务看板、测试结论与 `PRD` 冲突时，必须先修正文档结论，不得保留误导性“已对齐”描述。
6. 状态管理不得混淆：
   - 仅完成设计，不得标 `done`
   - 代码完成但联调被数据阻塞，应保留 `doing` 或标注 `blocked`
   - 只有业务验收通过后才能标 `done`
7. 当审查、联调或编码过程中发现新的 `PRD` 缺口时，必须先回填到当前需求的 `任务看板` 和必要的 `需求池状态说明`，再继续实现；不允许只在聊天里记录。
8. 一个任务只允许对应一个明确的 `PRD` 缺口或一个明确的交付物；禁止把多个未收口 `PRD` 缺口合并成一条任务。
9. 任何代码、SQL、测试、状态结论变更，只要会使现有文档失效或过时，必须在同一回合同步更新对应文档；不允许留下“代码已改、文档待后补”的状态。

## 文档同步范围

至少检查并按需同步：

1. `需求池`
2. `任务看板`
3. `PRD追溯清单`
4. `流程图与实现对齐说明`
5. `测试结果 / 联调记录`

提交前必须自查这些文档是否因本次改动而过期；若过期，先修文档再提交。
