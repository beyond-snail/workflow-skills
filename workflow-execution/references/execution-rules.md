# 执行侧独有规则

本文件只描述 `workflow-execution` 独有的执行约束。
共享治理基线仍以 `references/shared-governance.md` 为准。

## 数据库类需求

在以下场景优先读取：

1. `PRD`
2. `产品确认清单`
3. `流程图与实现对齐说明`

业务语义永远以 `PRD` 为准；字段、索引、类型风格优先参考当前项目已接入且可连通的数据库事实源，不写死环境名。

## 批处理 / 结转性能要求

数据库类、批处理类、结转类任务至少遵守：

1. 对大批量 `IN (...)` 条件主动评估参数规模，必要时拆批，不要等数据库报错后再处理。
2. 避免逐条“查是否存在 -> update / insert”式 N+1 写法，优先数据库原生 `upsert` 或批量写入。
3. 避免逐条 `updateById`、逐单查询明细或汇总，优先先批量取数、内存分组、批量更新。
4. 对“删除历史失效数据”这类场景，避免超长 `NOT IN (...)`，优先采用分批读取后比对删除或其他可控方案。

## 可维护性要求

1. 长调用链方法需要补方法级和分段级注释，至少写清楚：
   - 干什么
   - 条件是什么
   - 得到什么
   - 为了什么
   - 对齐哪段 `PRD`
2. 查询结果类、聚合类、临时承载类的关键字段应补语义说明，避免后续维护只能靠字段名猜含义。
3. 当某些结构字段不是 `PRD` 明确要求的业务维度时，不要默认把它们放进业务过滤条件；先确认它们是存档字段还是业务口径字段。

## 构建与私服

1. 构建、测试、发布命令优先读取项目提供的配置，不要默认套公网模板。
2. 若项目启用了私服或自定义 settings / registry，必须优先使用项目指定配置。

## 状态与阻塞

收口时必须区分：

1. 研发完成
2. 联调阻塞
3. 验收完成

不得把“代码完成但数据阻塞”直接写成需求 `done`。

## 测试阻塞与替代验证

当验证被样本或环境阻塞时，必须同步输出：

1. 阻塞原因
2. 已完成的替代验证
3. 剩余待验证点

可接受的替代验证包括：

1. 真实业务样本期验证
2. 合成样本自动化验证
3. 数据库直接校验 SQL
4. `UAT` 测试用例文档

## 回退 / 重做

1. 任务执行中如发现方向错误，可把任务从 `doing` 回退到 `todo`，并注明回退原因。
2. 如已发现客观阻塞，应改为 `blocked`，并记录阻塞原因、替代验证和下一步动作。
3. 已提交代码如需回滚，优先通过新的修复提交或 `revert` 提交处理，不直接覆盖历史结论。
