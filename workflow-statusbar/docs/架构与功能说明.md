# workflow-statusbar 架构与功能说明

## 1. 项目定位

`workflow-statusbar` 是 `workflow-skills-copy` 仓库中的桌面端子工程，用来把本机 `Codex` 会话状态和接入 `workflow` 底座的项目状态聚合成一个统一的桌面状态面板。

它的目标不是做完整项目管理系统，而是做一个常驻型“运行驾驶舱”：

- 持续监听 `Codex` 是否仍在执行
- 自动发现当前机器上最近活跃的 workflow 项目
- 展示项目所处阶段、当前任务、阻塞状态、Token 使用情况
- 在关键状态变化时触发本机提醒或远程提醒

产品形态上，它目前是一个菜单栏 / 托盘型桌面工具：

- 托盘入口
- 主状态面板
- 提醒配置面板
- 关键事件通知

## 2. 整体架构

项目采用 `Tauri 2 + Rust + React` 的前后端分层架构。

### 2.1 架构分层

#### 桌面宿主层

- `Tauri 2`
- 负责托盘、窗口、命令调用、事件分发、系统通知、单实例约束

#### 状态聚合层

- `Rust`
- 负责读取本机 `~/.codex` 数据和项目 `.ai/runtime/project-state.json`
- 负责把多来源状态整理为统一的 `RuntimeState`
- 负责状态轮询、变化检测、自动提醒、远程提醒下发

#### 展示层

- `React 19 + TypeScript + Vite`
- 只消费后端给出的统一状态对象，不直接读取本地数据库或文件
- 负责渲染主卡片、设置面板、空状态

### 2.2 核心运行链路

运行链路可以概括为：

`本地 Codex / workflow 状态源`
-> `Rust 轮询聚合`
-> `统一 RuntimeState`
-> `Tauri emit(runtime-state)`
-> `React 渲染面板`

关键点：

- Rust 是唯一的状态真相源
- 前端不自行推断业务状态，只展示聚合后的结果
- 状态变化检测和通知逻辑也放在 Rust 侧，避免前端重复计算

## 5. 状态来源与数据模型

## 5.1 状态来源

`workflow-statusbar` 当前主要读取四类信息：

### Codex 运行态

- `~/.codex/state_5.sqlite`
- `~/.codex/logs_2.sqlite`
- `pgrep -f "codex"`

用于判断：

- 当前是否有 `Codex` 进程
- 活跃线程是谁
- 最近一条消息和角色
- 最近心跳时间
- 是否处于运行、等待输入、卡住、离线等状态

### workflow 项目运行态

- 就近项目目录下的 `.ai/runtime/project-state.json`

用于判断：

- 当前项目处于 `bootstrap / requirement / execution / done` 哪个阶段
- 当前需求、当前任务、任务状态
- Gate、Health、Risk、是否阻塞
- 最近同步时间
- 是否启用了自动续跑

### IDE 打开项目线索

Rust 侧会结合线程工作目录、项目路径等信息，推断哪些项目是当前机器上“正在被关注的项目”。

### 提醒配置

- Tauri 应用配置目录下的 `alert-settings.json`
- 如果本地配置不存在，则回退到环境变量

## 5.2 统一运行态模型

后端最终会把多源数据汇总成统一的 `RuntimeState`，主要包括：

- `codex`
  - 当前 Codex 全局状态
- `projects`
  - 所有已识别项目的快照列表
- `groups`
  - 项目分组视图数据
- `summary`
  - 各阶段项目统计
- `spotlight_project`
  - 当前最值得展示的焦点项目
- `updated_at`
  - 本次聚合时间

其中单项目快照 `ProjectSnapshot` 会带上：

- 项目名、路径
- workflow 阶段
- gate / health / risk
- 当前需求与任务
- 当前任务状态
- Codex 线程与心跳
- Token 总量、输入、输出、推理量
- 自动续跑是否启用
- 是否被判定为阻塞

## 6. 状态判定机制

当前项目对 `Codex` 的运行状态做了统一枚举：

- `running`
- `waiting_input`
- `stalled`
- `idle`
- `offline`

大体判定逻辑是：

- 有进程且心跳很新，判定为 `running`
- 有进程但心跳放缓，判定为 `waiting_input`
- 有进程但心跳超时，判定为 `stalled`
- 无进程，判定为 `idle`
- 连 `~/.codex` 状态都无法正常获取，判定为 `offline`

workflow 阶段则统一为：

- `bootstrap`
- `requirement`
- `execution`
- `done`
- `unknown`

这样前端只关心统一枚举，不需要理解底层的 sqlite、日志或项目文件细节。

## 7. 前后端交互方式

前后端交互主要通过两种机制完成：

### 7.1 Tauri Command

Rust 暴露了以下主要命令：

- `get_runtime_state`
  - 读取当前最新聚合状态
- `get_alert_settings`
  - 读取提醒配置
- `save_alert_settings_command`
  - 保存提醒配置
- `send_test_alert_command`
  - 发送测试提醒
- `toggle_main_window`
  - 切换主面板显示
- `open_alert_settings_window`
  - 打开提醒配置面板
- `sync_main_window_size`
  - 同步主窗口高度
- `set_floating_visibility`
  - 控制悬浮窗显示状态
- `open_path`
  - 打开项目目录

### 7.2 Tauri Event

Rust 侧会主动向前端发事件：

- `runtime-state`
  - 推送最新聚合结果
- `open-alert-settings`
  - 通知前端切到提醒配置面板

这意味着前端启动时先 `invoke` 拉一次初始数据，随后通过事件持续接收增量更新。

## 8. 窗口与托盘机制

## 8.1 主窗口

`tauri.conf.json` 当前实际定义了一个窗口：

- `label = main`
- 无边框
- 透明
- 常驻最前
- 默认隐藏
- 不出现在任务栏

这个窗口用于承载主状态面板和提醒配置面板。

## 8.2 托盘

Rust 通过 `TrayIconBuilder` 构建托盘图标，并挂接菜单项：

- 打开面板
- 提醒配置
- 退出

左键托盘图标时：

- 如果面板已显示，则隐藏
- 如果面板未显示，则按托盘位置弹出

窗口失焦后会自动隐藏，因此它更像一个状态弹层，而不是传统桌面主程序。

## 8.3 单实例

项目启用了 `tauri-plugin-single-instance`：

- 如果再次启动应用，不会开第二个实例
- 会直接拉起已有主窗口

## 9. 前端组件职责

当前前端入口主要以 `App.tsx` 为中心。

### 9.1 已实际接入的组件

- `AppShell`
  - 提供统一壳层和布局容器
- `StatusCard`
  - 主状态卡片，也是当前 dashboard 的核心内容
- `AlertSettingsPanel`
  - 远程提醒、本机提醒、事件矩阵等配置页
- `EmptyState`
  - 初始加载失败或无数据时的占位状态

当前 dashboard 实际是：

- 1 个焦点项目的大卡片
- 若存在多个已打开项目，则继续渲染多个紧凑版 `StatusCard`

### 9.2 代码中已存在但当前未主链路接入的组件

- `FloatingCard`
  - 小悬浮执行卡片
- `FocusCard`
  - 项目焦点卡片
- `ProjectGroups`
  - 项目分组折叠面板

这些组件说明项目已经为“多项目聚合”和“执行中小窗”做了 UI 预留，但当前主入口还没有把它们完整接进正式渲染链路。

## 10. 当前已实现功能

基于现有代码，`workflow-statusbar` 已经具备以下功能：

### 10.1 Codex 运行态监控

- 监控本机 `Codex` 是否在线
- 显示活跃线程名、最近消息、最近心跳
- 区分运行中、等待输入、可能卡住、空闲、离线

### 10.2 workflow 项目状态展示

- 自动读取项目 `.ai/runtime/project-state.json`
- 展示当前项目所处阶段
- 展示当前需求 / 当前任务
- 展示 Gate、Health、Risk、阻塞状态
- 展示 Token 消耗
- 展示自动续跑状态

### 10.3 多项目基础聚合

- 能识别多个项目快照
- 能输出 `summary` 和 `groups`
- 主面板可展示多个打开项目的状态卡

不过当前“项目分组视图”虽然有数据结构和组件准备，但还没有成为主界面默认交互。

### 10.4 托盘交互

- 托盘左键开关面板
- 托盘菜单打开提醒配置
- 托盘菜单退出应用

### 10.5 本机提醒

- 对关键状态变化触发桌面通知
- 支持测试提醒

通知事件粒度已覆盖：

- 任务完成
- 项目完成
- 项目阻塞
- 任务中断
- 自动续跑失败

### 10.6 远程提醒

已支持两种远程提醒模式：

- `bridge`
  - 先发给自建 HTTP 桥接服务，再转发到飞书等外部平台
- `feishu`
  - 由桌面端直接调用飞书应用接口发送消息

配置项可以在前端提醒设置面板里保存，Rust 侧负责本地持久化。

### 10.7 项目目录快捷打开

前端可调用 `open_path`，直接从状态卡跳转到项目目录，方便开发时快速回到工程现场。

## 11. 提醒系统设计

提醒系统不是简单“有变化就推送”，而是带有配置矩阵的统一告警入口。

支持控制的维度包括：

- 本机通知总开关
- 远程通知总开关
- 每类事件是否发本机
- 每类事件是否发远程
- 远程通道模式选择

当前提醒能力比较适合作为“执行守护层”：

- 人不盯着终端，也能知道任务是否卡住
- 项目进入阻塞或完成时能及时感知
- 可以把桌面端状态同步到飞书

## 12. 轮询与更新机制

Rust 侧会启动后台线程，按固定周期重新聚合运行态。

当前代码中的轮询周期为：

- `8 秒`

每次轮询会做两件事：

- 刷新最新 `RuntimeState`
- 对比上一次状态签名，判断是否要触发提醒

因此这个项目本质上是一个“轮询聚合 + 变化检测 + 事件驱动 UI”架构，而不是复杂的实时订阅架构。

这样做的优点是：

- 实现简单稳定
- 对现有 `workflow` 文件结构侵入小
- 不依赖额外守护进程

## 13. 实现边界与当前不足

从现有代码看，这个项目已经有较完整的 MVP，但也存在几个边界需要说明。

### 13.1 小悬浮窗能力目前更像预留能力

Rust 命令里已经有：

- `set_floating_visibility`

前端也有：

- `FloatingCard`

但当前 `tauri.conf.json` 只显式定义了 `main` 窗口，前端主入口里也没有把 `floating` 窗口渲染链路真正跑起来。

这说明：

- “执行中悬浮窗”方向已经设计过
- 但当前正式落地的主能力仍然是托盘主面板，不应把悬浮窗视为已完整上线能力

### 13.2 组件预留多于实际接线

像 `FocusCard`、`ProjectGroups` 已经存在，但当前主入口默认仍是 `StatusCard` 驱动的简单卡片流。

说明项目正在从 MVP 向更完整的多项目监控面板演进。

### 13.3 平台能力当前偏向 macOS

代码里有：

- `macos-private-api`
- `open` 命令
- 托盘 / 顶部弹层交互

所以当前体验明显更贴近 macOS 菜单栏工具，虽然 Tauri 理论上可跨平台，但实际主体验和调优重点还是 macOS。

## 14. 适合的使用场景

`workflow-statusbar` 适合以下场景：

- 本机同时跑多个接入 workflow 的项目
- 不想一直盯着终端，但想知道 Codex 有没有卡住
- 想从桌面快速看到当前任务、阶段、阻塞情况
- 想把任务异常或完成状态同步到飞书

它特别适合作为 `workflow-bootstrap / workflow-requirement / workflow-execution` 三个 skill 的桌面可视化补充层。

## 16. 一句话总结

`workflow-statusbar` 本质上是一个基于 `Tauri + Rust + React` 的本地运行态聚合器：Rust 负责读取 `Codex` 与 `workflow` 状态、做判断和告警，React 负责把这些状态渲染成可快速浏览的桌面监控面板。

如果把三个 workflow skill 看成“生成规则和执行链路”，那 `workflow-statusbar` 就是这一套协作底座的“桌面观察层”。
